## 3 分钟导读

**一句话定位**：以民法典/公司法/反法/消法/劳动法/劳动合同法六部法（1868 条）为知识库的法律问答系统——1.0 靠 Coze 低代码 prompt 和人肉评测扛，2.0 把决定效果的六个环节全部换成了系统能力。

**六项工业化升级**（1.0 → 2.0）：

| # | 环节 | V1.0 | V2.0 |
|---|---|---|---|
| 1 | 评测 | 人工 MOS 三分制（0–2），一次性 | **五分制（1–5）+ LLM-as-judge + 校准门禁 + 回归脚本** |
| 2 | 检索 | 平台内置 RAG，500 字定长切片 | **BGE-M3 dense/sparse 双路 + 查询扩展 + RRF(k=60) 融合，法条级切分** |
| 3 | 知识库 | 《民法典》单部（OCR） | **6 部法 1868 条**，带版本 / 时效字段，双版本并存 |
| 4 | 结构化 | 无 | **SQLite 法条表 + 法理别名表（1663 条）** |
| 5 | 工程 | Coze 工作流 | **Python 核心链路 + FastAPI 服务 + 可观测面板 + React 前端** |
| 6 | 安全 | Prompt 约束 + 零召回熔断 | **引用溯源校验（机器比对）+ 知识边界自白 + 置信度门控** |

## 产品定义

**用户是谁**（20 人问卷，1.0 阶段调研资产，2.0 沿用）：

| 用户层 | 占比 | 需求 | 对回答格式的约束 |
|---|---|---|---|
| 临时查（客服 / 运营） | 50% | 大白话解释，事件驱动 | 少术语、先给结论 |
| 定期查（组长 / PM / HR） | 25% | 场景分析 + 解决方案 | 要有行为指导，且不能越界给激进建议 |
| 专业查（法务 / 风控） | 25% | 法条编号精准引用 | 首句即给法条编号与原文 |

**三条痛点** → 直接定义了回答格式：法条晦涩、信息源混乱易混入过期版本、搜索结果抓不住重点 → **三段式**（引用法条 → 通俗解释 → 行为指导）。

**核心差异化**：市面上能答法律问题的 RAG demo 很多；能拿出「改了 12 个版本、其中 3 个是负结果、每次改动都有预注册门禁」的项目极少。这个项目的价值不在「能答对」，而在**知道自己答得对不对、差在哪、为什么**。

## 技术栈形式：混合栈

> **Python 核心链路 + 低代码外围**。1.0 的 Coze 工作流保留为历史归档，2.0 把决定效果的部分（检索 / 决策 / 评测 / 校验）全部收回代码，只把展示与配置留在轻量层。

| 层 | 选型 | 关键约束 / 为什么 |
|---|---|---|
| 知识库 | 民法典、公司法、反不正当竞争法（2025）、消费者权益保护法、劳动法、劳动合同法，共 1868 条 | **法条级切分（一条 = 一行）**：检索单元 = 引用单元，法条号直接映射 chunk id，引用溯源退化为字符串比对 |
| 向量 / 检索 | BGE-M3（dense + sparse）、Qdrant 本地、RRF 融合 k=60、查询扩展（DeepSeek） | 检索成本近乎为零；**reranker 两次验证为负优化后永久弃用** |
| 决策 | **JEV（`jev-1.13.0`，System One 决策模型）** | 分类任务不需要生成能力：输出带校准置信度、结构化零解析错误、单次 70–500ms。用于意图路由（5+1 路分发）与证据充分性门控 |
| 生成 | Doubao（默认）/ DeepSeek；**按意图路由到 6 套独立 prompt** | 每路一个 prompt 文件，防长文本指令稀释，且各模板可独立版本化 |
| 评测 | 五分制五维 MOS + **LLM-as-judge（qwen-plus）** | judge 先校准再使用（±1 一致率 86.7%，Pearson 0.893）；judge 有 rationale，可支撑 Badcase 归因 |
| 引用安全 | 确定性正则审计（`CIT_RE` / `INLINE_RE`）+ `quote_ratio` 分级 | 不用模型判断「引用是否真实」，用代码比对字符串 |
| 服务 | Python / FastAPI + SSE | `/api/chat` 流式推送 S0–S5 状态 |
| 存储 | SQLite（`app.db`） | `requests` / `audit` / `sessions` / `turns` 四张表 |
| 前端 | React + Vite + TypeScript + AntD | 两页：对话页 + 管理后台 |
| 观测 | Streamlit 面板（`app.py`，旧链路，保留只读） | 链路可视化 / 评测对比 / 法条库浏览 |

**三个选型判断**（面试高频追问）：

1. **生成用 LLM、判断用决策模型** —— 按任务类型选原语，不是无脑全上 LLM。
2. **法条级切分** —— 对齐引用单元，固定长度切片会拆碎溯源能力。
3. **reranker 永久弃用** —— 它会把已命中的正确条挤出 top-10（两次复现），负结果写进黑名单。

## 系统链路

```
用户 query
  → S0 意图路由        JEV：意图 Choice（5+1 路分发）+ false_premise Noul
  → S1 首轮检索        原 query + 3 变体 × dense/sparse → RRF → top-10
  → S2 充分性门控      JEV：证据够不够，不够就进追加轮
  → S3 追加轮          ≤2 轮，生成缺口查询重检
  → S4 生成            按意图路由到 6 套独立 prompt
  → S5 引用校验        机器比对 + quote_ratio 分级
```

## 功能需求与验收口径

| 编号 | 需求 | 验收口径 |
|---|---|---|
| FR-1 | 自然语言提问 → 三段式回答（引用法条 / 通俗解释 / 行为指导） | 五维 MOS 完整性 ≥4.0；三段缺一即不合格 |
| FR-2 | 法条引用可追溯、可点击展开原文 | 引用审计 `outside_context = 0` |
| FR-3 | 知识库无依据时拒答，不编造 | 零召回熔断 + 对抗样本 veto PASS |
| FR-4 | 复杂 / 隐性事实问题可多轮追加检索 | ReAct 追加轮 ≤2；复合切片召回 ≥0.95 |
| FR-5 | 同一对话框内多轮追问（指代、条件变体） | 轮 2「那超过一年没签呢」意图沿用、`outside_context = 0` |
| FR-6 | 链路过程可观测（S0–S5 状态、命中法条、门控结论） | 对话页时间线逐步可见 |
| FR-7 | 知识库可查看 / 编辑，配置可切换，评测与使用数据可查 | 管理后台四 Tab，编辑留审计日志 |
| FR-8 | 面试演示可稳定复现 | 演示模式输出不随历史 / 随机性变化 |
| NFR-1 | 引用不得虚构 | 六版零 `outside_context` |
| NFR-2 | 评测可复现 | 模型 pin 版本、prompt 文件 hash 入报告、预注册门禁 |
| NFR-3 | 单轮基线不因功能增加而漂移 | 空历史时 7 个调用点 prompt 逐字节一致 |
| NFR-4 | 密钥不入库 | 全部走 `.env`，代码库无明文 |
| NFR-5 | 延迟与成本可解释 | 端到端约 30s，检索成本近零 |

## 关键指标（截至白皮书数据日期 2026-10-27）

| 维度 | 结果 |
|---|---|
| 检索（v2 primary） | 显性 1.00 / 隐性 1.00 / 推理 0.88 / **mean 0.983** |
| 生成（v1.2 冻结） | **MOS 4.46**（准确 4.4 / 相关 4.3 / 完整 4.2 / 简洁 4.4 / 安全 5.0） |
| 引用安全 | **六版零 outside_context** |
| 意图路由 | 0.95（v1）→ 0.533（v2 口语化）→ **0.800**（加口语判据后） |
| ReAct 循环 | v2 mean recall 0.933 → **0.983**；复合切片 0.75 → **1.00**；对抗 veto FAIL → **PASS** |
| 机制实证 | id29 错误前提题 `false_premise=0.94` → 纠错式重查 → 补回劳动合同法第 21 条 → judge **5.0 / 4.8** |

> 1.0 基线（不同量纲，仅作历史对照）：Precision 0.44 → 0.63、F1 0.49 → 0.57、MOS 单轮 2.00 / 2.00、多轮 1.92 / 2.00。
> **口径提醒**：1.0 的 2.00 与 2.0 的 4.46 是不同量纲，不可直接比较；1.0 单部民法典与 2.0 六部法也不共基线。

## 已知缺陷（诚实清单，不掩饰）

1. id7 多跳弱信号：两轮追加检索都被强信号带偏，劳动合同必备条款始终没召回。
2. id2 / id10 生成选条失败：正解都在 top-10，两轮 prompt 干预未纠正 —— 生成模型选择能力上限，非检索缺陷。
3. 意图路由 0.800 未达 0.85：剩余错例中 5 个是复合语义题，单标签装不下复合语义，属标注体系局限。
4. 生成侧非确定性：检索 + 意图 30/30 逐条一致，但生成文本 100% 不同（供应商 API 在 t=0 仍抖动）。
5. 循环的隐性代价：secondary 覆盖率 0.625 → 0.562；引用 verbatim 率随上下文变大而下降（是「改写」不是「虚构」）。
6. 门控偏松：约 90% query 判「证据不足」进入循环 —— 召回赚满但成本没省下。

## 成本与性能

| 项 | 数值 |
|---|---|
| 端到端延迟 | **约 30 秒 / query**（检索层 3.5s + 生成段 29–31s） |
| ReAct 循环 | 平均 1.73 轮 / query，30 题中 27 题进循环 |
| Token | JEV 约 1311 in / 87 out；生成模型调用另计 |
| 检索成本 | 近乎为零（本地 BGE-M3 + Qdrant） |

> 面试时说「检索 3.5 秒」是误导，用户感知的是 30 秒。这是用智能换召回的典型权衡：多花 27 秒换 5 个百分点的召回。
