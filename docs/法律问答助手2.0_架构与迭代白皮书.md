# 法律条文问答助手 2.0 · 架构与迭代白皮书

> 面向读者：面试官 / 产品评审
> 定位：作品集文档（叙事优先，技术细节服务于"这个系统为什么可信"）
> 数据截止：2026-10-27

---

## 一、这个产品是什么

**一句话**：一个可自证效果的领域 RAG 系统——它输出法律答案，但真正的产品资产是"这个答案为什么可信"的证据链。

**用户分层**（来自 20 人问卷，1.0 阶段的调研资产）：

| 用户层 | 占比 | 需求 |
|---|---|---|
| 临时查（客服/运营） | 50% | 大白话解释，事件驱动 |
| 定期查（组长/PM/HR） | 25% | 场景分析 + 解决方案 |
| 专业查（法务/风控） | 25% | 法条编号精准引用 |

用户痛点三条：法条晦涩、信息源混乱易混淆过期内容、搜索结果抓不住重点。**第三条直接定义了回答格式**——三段式（引法条 → 通俗解释 → 行为指导）。

**为什么"自证效果"是核心**：市面上的 RAG demo 都能答法律问题。能拿出"我改了 12 个版本、其中 3 个是负结果、每次改动都有预注册门禁"的项目极少。**这个项目的差异化不在它能答对，在它知道自己答得对不对、差在哪、为什么。**

## 二、1.0 → 2.0：六个工业化升级

1.0 是低代码平台（Coze）上的原型，有用户调研、竞品对比、四场景理想态、MOS 三分制评测——**评测意识在 1.0 就存在，但停留在"人肉逐条打分"**。2.0 把它变成系统能力：

| # | 升级 | 1.0 | 2.0 |
|---|---|---|---|
| 1 | 评测 | 人工 MOS 三分制，一次性 | 五分制 + LLM-as-judge + 校准门禁 + 回归脚本 |
| 2 | 检索 | 平台内置 RAG，500 字切片 | BGE-M3 双路 + 查询扩展 + RRF 融合，法条级切分 |
| 3 | 知识库 | 民法典（OCR） | 6 部法 1868 条，带版本/时效字段，双版本并存 |
| 4 | 结构化 | 无 | SQLite 法条表 + 法理别名（1663 条） |
| 5 | 工程 | Coze 工作流 | Python 核心链路 + 可观测面板 |
| 6 | 安全 | Prompt 约束 | 引用溯源校验（机器比对）+ 知识边界自白 + 置信度门控 |

**设计主线**：把 1.0 里"靠 prompt 和人肉扛"的六个环节，换成系统能力。

## 三、评测驱动的迭代史（核心章）

### 3.1 检索侧：九版消融

| 版本 | 改动 | 隐性切片 | 结论 |
|---|---|---|---|
| v0 | 纯文本 + hybrid RRF（基线） | 0.50 | — |
| v0.1 | 嵌入富化（编章节标题拼接） | 0.50 | **无效**（RRF 只认名次不认分数） |
| v0.2 | reranker 精排 | 0.40 | **负优化**（救回 1 条、赔掉 1 条） |
| v0.3 | query 扩展 + best-rank 融合 | 0.60 | 新高，但融合实现偏离规格 |
| v0.4 | 扩展池 + reranker | 0.40 | 负优化复现，**reranker 永久弃用** |
| v0.5 / v0.5b | 法理别名表 | 0.50 / 0.60 | 引入显性回退，不可冻结 |
| **v0.6-rrf-alias** | 扩展 + RRF(k=60) + 别名 | **0.60 全绿** | **冻结选定** |

三个负/平结果全部留档，并写进"被否决方向黑名单"（防止未来重复实验）：reranker 精排、稀疏路加权、best-rank 融合主键。

**方法论**：门禁在实验**前**写死（显性 ≥0.90 / 隐性 ≥0.70 / 对抗一票否决），实验后**不为过线调参**。v0.2 和 v0.4 两次负结果都直接弃用，没有"再调一轮试试"。

### 3.2 生成侧：三版迭代

| 版本 | 总体 MOS | 关键改动 |
|---|---|---|
| v1.0 | 4.26 | 基线（judge 修正口径） |
| v1.1 | 4.34 | 四合一：prompt 简洁性预算 + 知识边界自白 + JEV 意图路由 + 扩展变体离线固化 |
| v1.2 | 4.46 / 4.37 | 选条通则 + 模板信息密度硬约束 |

**一个被数据推翻的预判**：我以为"简洁性收紧必然牺牲完整性"（帕累托张力），实测两者同时上升——**先测量再下结论，别用直觉定验收线。**

### 3.3 ReAct 循环检索

| 指标 | 基线 | ReAct |
|---|---|---|
| v2 mean recall | 0.933 | **0.983** |
| 复合切片 | 0.75 | **1.00** |
| 对抗 veto | FAIL | **PASS** |

**最有价值的一步是"先定量靶子"**：id12 复合题整题查 0.50、拆开查两半各 1.00——把"任务分解能拿的分"提前量化成 0.5，再让 ReAct 去拿。这是把想法变成可测量命题的关键。

机制实证：id29（对抗题）`false_premise=0.94` 触发纠错式重查 → 追加轮补回劳动合同法第 21 条 → judge 分 **5.0 / 4.8**。

## 四、测量仪器的四次修正（最硬的一章）

> 一个评测系统的可信度，取决于它发现并修正自身缺陷的能力。这个项目修正了三次仪器级缺陷，还有一次是我的误判。

| # | 缺陷 | 怎么发现的 | 修正 |
|---|---|---|---|
| 1 | **融合实现偏离规格**：规格写 RRF 求和，实现成了"最佳位次主键排序"，导致单点火种永远进不了 top-10 | 检索归因时追踪 dense/sparse 双路位次 | 改回 RRF 求和 + 回溯重判两个历史版本 |
| 2 | **judge 知识边界**：judge 用自身（过时）法条记忆判"编造"，冤枉了引用 2025 版反法第 13 条的答案 | id16 低分的判词里写着"反法无第 13 条" | judge prompt 注入语料清单，明确"存在性以语料为准，禁止凭记忆判编造"，并回溯重判 |
| 3 | **judge 上下文丢失**：评测脚本预载了已完成答案，新生成答案的检索上下文没传给 judge | 代码审查 | 修复 + 回溯重判 |
| 4 | **我的误判**：我推测 sufficiency 门控是"检索前盲判"，据架构图核实——门控在检索之后，判断错误 | 用户贴架构图纠正 | 不改实现；但顺带发现真问题：门控 state 只给条号清单、不给条文内容，导致它测的是"题难不难"而非"缺不缺证据"（v3 议题） |

**第 1、2 条的通用意义**：LLM-as-judge 有一个系统性缺陷类别——**judge 的世界知识与被评测系统的知识库不同步时，会系统性冤枉"引用了新知识"的答案**。法律场景法条年年修订（反法 2025、公司法 2023），任何模型训练数据都滞后，这个 bug 必然复发。

## 五、架构与组件选型

```
用户 query
  → S0 意图路由（JEV 决策模型：intent Choice + false_premise Noul）
  → S1 首轮检索（原 query + 3 变体 × dense/sparse → RRF → top-10）
  → S2 证据充分性门控（JEV）
  → S3 追加轮（≤2 轮，生成缺口查询重检）
  → S4 生成（按意图路由到 6 套独立 prompt）
  → S5 引用校验（机器比对 + quote_ratio 分级）
```

**三个选型判断**（面试会被追问"为什么这么选"）：

| 选型 | 理由 |
|---|---|
| **意图分类用 JEV（决策模型）而非 LLM** | 分类任务不需要生成能力。JEV 输出带校准置信度、结构化零解析错误、单次 70-500ms、输出免费——比 LLM 分类快一个量级。生成用 LLM、判断用决策模型，按任务类型选原语 |
| **切分用法条级（一条 = 一行）而非固定长度** | 检索单元 = 引用单元：法条号直接映射 chunk id，引用溯源变成字符串比对。固定切片会拆碎这个能力 |
| **reranker 两次验证后永久弃用** | 它会把已命中的正确条挤出 top-10（两次复现）。负结果写进黑名单 |

## 六、当前能力边界与已知缺陷（诚实清单）

| 指标 | 当前值 |
|---|---|
| 检索（v2，primary 口径） | 显性 1.00 / 隐性 1.00 / 推理 0.88 / mean 0.983 |
| 生成（v1.2） | MOS 4.46（准确 4.4 / 相关 4.3 / 完整 4.2 / 简洁 4.4 / 安全 5.0） |
| 引用安全 | **六版零 outside_context**（从未编造法条） |
| 意图路由 | 0.95（v1）→ 0.533（v2 口语化）→ **0.800**（修正后） |

**已知缺陷（全部归档，不掩饰）**：

1. **id7 多跳弱信号**：两轮追加检索都被"抽逃出资"的强信号带偏，劳动合同必备条款始终没召回——多跳弱信号侧是当前检索的能力上限
2. **id2/id10 生成选条失败**：正解都在 top-10，两轮 prompt 干预未纠正——生成模型的选择能力上限，非检索缺陷（归因已隔离）
3. **意图路由 0.800 未达 0.85**：剩余 6 个错例中 5 个是复合语义题——**单标签装不下复合语义**，属标注体系局限，非分类器缺陷（v3：改多标签或按 part 判）
4. **生成侧非确定性**：检索+意图 30/30 逐条一致，但生成文本 100% 不同（供应商 API 在 t=0 仍抖动）——评测场景由离线固化兜住，生产环境措辞漂移对用户无感
5. **循环的隐性代价**：secondary 覆盖率 0.625 → 0.562（追加轮挤占 top-10 名额）；引用 verbatim 率随上下文变大而下降（v1.1 86.8% → v21 69.8-81.4%）——**是"改写"不是"虚构"**
6. **门控偏松**：90% 的 query 判"证据不足"进入循环——宁可多查的性格，召回赚满但成本没省下（v3 议题）

## 七、成本账

| 项 | 数值 |
|---|---|
| 端到端延迟 | **约 30 秒 / query**（检索层 3.5s + 生成段 29-31s） |
| ReAct 循环 | 平均 1.73 轮 / query，30 题中 27 题进循环 |
| Token | JEV 约 1311 in / 87 out；生成模型调用另计 |
| 检索成本 | 近乎为零（本地 BGE-M3 + Qdrant） |

**诚实提示**：面试时说"检索 3.5 秒"是误导，用户感知的是 30 秒。这是一个用智能换召回的典型权衡——多花 27 秒换 5 个百分点的召回。

## 八、面试速答卡

| 追问 | 答法要点 |
|---|---|
| 效果怎么测的？ | 五分制五维 + LLM-as-judge，**先校准再使用**（±1 一致率 86.7%，Pearson 0.893），预注册门禁，双跑确定性验证 |
| 遇到负结果怎么办？ | 两个负结果（富化无效、reranker 负优化）全部留档进黑名单，不调参、不掩饰 |
| 你怎么知道 judge 可信？ | 校准 + **发现并修正了 judge 自身的两个缺陷**（知识边界、上下文丢失），并回溯重判历史版本 |
| 为什么停在这个数字？ | 30 条 query 已被 12 个配置反复压过，继续优化是过拟合。**我知道什么时候该停** |
| 引用会不会编造？ | 六版零 outside_context，机器校验 quote_ratio 分级（原文/改写/未命中），问题在"改写保真度"不在"虚构" |
| 最大的设计决策？ | 按任务类型选模型原语：生成用 LLM、分类判断用决策模型；切分对齐引用单元 |
| 如果重做一次？ | 会更早建新评测集（v1 的 20 条在第 9 个版本时已饱和，我应该更早扩集） |
